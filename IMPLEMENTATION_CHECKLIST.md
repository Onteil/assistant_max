# Чек-лист реализации эскалации технической поддержки

## ✅ Требования из контекста разговора

### 1. Архитектура эскалации
- ✅ **3-уровневая эскалация**: Level 0→1 (10 мин), Level 1→2 (20 мин), Level 2→Admins (30 мин)
- ✅ **Текущая архитектура сохранена**: Заявки отправляются всей группе поддержки изначально
- ✅ **Дедупликация**: Каждый резервный менеджер получает только ОДНО уведомление

### 2. Функциональность
- ✅ **_escalate_technical_support_to_backup_level_1()**: Собирает всех backup_manager_1, дедуплицирует, отправляет уведомления
- ✅ **_escalate_technical_support_to_backup_level_2()**: Собирает всех backup_manager_2, дедуплицирует, отправляет уведомления
- ✅ **_escalate_technical_support_to_admins()**: Уведомляет администраторов и каналы эскалации
- ✅ **Роутинг в _check_technical_support_ticket_async()**: Правильно направляет на нужную функцию по escalation_level

### 3. Дедупликация резервных менеджеров
- ✅ Используется `set()` для сбора уникальных ID резервных менеджеров
- ✅ Один менеджер получает только одно уведомление, даже если он резервный для нескольких сотрудников

### 4. Установка assigned_staff_id
- ✅ **backup_escalation.py обновлен**: При взятии заявки резервным менеджером он становится assigned_staff_id
- ✅ **Разделение логики**: Для INVOICE/RENEWAL проверяется назначение, для TECHNICAL_SUPPORT/CONSULTATION любой резервный может взять

### 5. Поддержка обоих типов заявок
- ✅ **TECHNICAL_SUPPORT**: Получает сотрудников с ролью TECHNICAL_SUPPORT
- ✅ **CONSULTATION**: Получает сотрудников с is_estimate_tech_specialist=True

### 6. Использование MAX_Messenger_Data
- ✅ Все функции используют правильный lookup: `MAX_Messenger_Data.max_chat_id` по `max_user_id`
- ✅ Не используется `staff_members.max_chat_id` (который NULL)

### 7. Graceful fallback
- ✅ Если нет support staff → эскалация к админам
- ✅ Если нет backup_manager_1 → переход к уровню 1 (попытка backup_manager_2)
- ✅ Если нет backup_manager_2 → эскалация к админам

### 8. Уведомления
- ✅ Кнопка "✋ Взять в работу" с правильным payload (BackupEscalationPayload)
- ✅ Информативные сообщения с деталями заявки
- ✅ Правильные escalation_level в payload (1 для level_1, 2 для level_2)

### 9. Логирование
- ✅ Action_Log создается с правильными деталями
- ✅ Логируется количество уникальных резервных менеджеров
- ✅ Логируется количество успешных/неудачных уведомлений

### 10. Планирование следующей проверки
- ✅ После каждого уровня планируется следующая проверка через get_escalation_timeout_sync()
- ✅ Используется check_technical_support_ticket.apply_async()
