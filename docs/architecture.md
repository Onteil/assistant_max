# Архитектура

## Компоненты

Приложение состоит из следующих процессов:

- FastAPI и webhook-обработчики в `main.py` и `api/`;
- MAX-бот в `bots/max_bot/`;
- опциональный Telegram-бот в `bots/tg_bot/`;
- бизнес-логика в `services/`;
- PostgreSQL с моделями из `database/models.py`;
- Redis для Celery и состояния ботов;
- Celery worker и Celery beat в `celery_app/`;
- SQLAdmin-панель, подключённая к FastAPI.

На сервере FastAPI, Celery worker и Celery beat запускаются отдельными systemd unit-файлами. Nginx принимает внешние запросы и проксирует их в Uvicorn на `127.0.0.1:8453`.

## Запуск ботов

`BOT_MODE` принимает значения:

| Значение | Запускаемые компоненты |
|---|---|
| `max` | только MAX-бот |
| `tg` | только Telegram-бот |
| `both` | оба бота |
| `none` | только FastAPI, admin и API |

Для выбранного канала необходим соответствующий токен. При `BOT_MODE=max` переменная `TG_BOT_TOKEN` может быть пустой.

## Основной поток данных

1. MAX передаёт событие webhook-обработчику FastAPI.
2. Handler проверяет пользователя и состояние сценария.
3. Сервисный слой изменяет данные в PostgreSQL и определяет получателя заявки.
4. Сообщение отправляется через MAX API либо сохраняется до подходящего рабочего режима.
5. Долгие, периодические и повторные операции выполняются Celery через Redis.
6. Важные действия фиксируются в `Action_Log`; временно неуспешные операции i-TAT сохраняются в очереди повторов.

## Основные сущности

- `User`, `Organization`, `GS_Key` — клиент, организации и ключи.
- `Staff_Member` — сотрудник, роль, рабочий статус, резервные менеджеры и признаки дежурства.
- `Ticket` — заявка, назначенный сотрудник, статус и данные маршрутизации.
- `Message`, `File_Attachment` — история переписки и вложения.
- `Calendar_Rule` — график и режим работы.
- `Action_Log` — журнал бизнес-действий.
- `API_Retry_Queue` — повтор временно неуспешных запросов к i-TAT.
- `NPS_Response`, `Notification_Event` — ответы NPS и запланированные уведомления.

## Celery

Worker должен слушать очереди:

```text
celery,nps_surveys,renewal_reminders,escalations,broadcasts,ticket_notifications,work_mode_monitor,api_retries
```

Beat запускает:

- очистку старых NPS-опросов ежедневно;
- проверку продлений ежедневно;
- резервную обработку очереди заявок ежедневно;
- проверку смены рабочего режима каждые 2 минуты;
- обработку очереди повторов i-TAT каждые 5 минут;
- очистку старых записей повторов ежедневно.

Для отложенных NPS-задач visibility timeout Redis установлен в 7 суток. Это предотвращает повторную доставку задач, запланированных примерно на сутки вперёд.

## Границы ответственности

- Handler отвечает за диалог, payload callback и состояние пользователя.
- Service отвечает за бизнес-правила и транзакции.
- Celery task отвечает за отложенный запуск и повтор, но не должен дублировать бизнес-логику.
- Messenger adapter отвечает за особенности MAX API и пересылку медиа.
- Webhook API не должен зависеть от доступности пользовательского чата.
