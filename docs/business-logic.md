# Бизнес-логика

## Рабочие режимы

Фиксированного времени работы в коде нет. Текущий режим определяется календарными правилами, настраиваемыми в административной панели:

- `REGULAR` — обычное рабочее время;
- `EXTENDED` — продлённое время с дежурными специалистами;
- `NON_WORKING` — нерабочее время.

Назначение дежурного сохраняется до изменения администратором. При смене режима Celery проверяет очередь каждые 2 минуты; дополнительный ежедневный запуск служит страховкой.

## Основные типы заявок

| Тип | `REGULAR` | `EXTENDED` | `NON_WORKING` |
|---|---|---|---|
| `INVOICE` | менеджер клиента | очередь | очередь |
| `RENEWAL` | менеджер клиента | очередь | очередь |
| `TECHNICAL_SUPPORT` | round-robin среди активных специалистов ТП | дежурный инженер | очередь |
| `CONSULTATION` | round-robin среди активных специалистов консультаций | дежурный консультант | очередь |

Для менеджерских заявок используется цепочка: основной менеджер клиента → резервный менеджер 1 → резервный менеджер 2 → активный администратор. Доступность сотрудника определяется признаками `is_active` и `is_working_today`.

Round-robin хранит ID последнего назначенного специалиста в настройках БД. Состояние сохраняется между перезапусками. Сам алгоритм не зависит от времени создания предыдущей заявки.

Если для текущего режима нет подходящего специалиста, уведомляются активные администраторы. Заявка остаётся доступной для ручного назначения.

## Очередь заявок

В `NON_WORKING` новые заявки не отправляются сотрудникам. В `EXTENDED` из очереди извлекаются только `TECHNICAL_SUPPORT` и `CONSULTATION`; `INVOICE` и `RENEWAL` ждут `REGULAR`.

Перед отправкой из очереди получатель определяется повторно:

- для счёта заново выполняется полная цепочка менеджеров;
- для продления проверяется доступность назначенного менеджера и при необходимости выполняется цепочка резервов;
- для техподдержки и консультации выбирается новый получатель согласно актуальному режиму.

После успешной отправки ставится отметка `queue_notification_sent_at` и запускается эскалация. При ошибке отправки отметка очищается, поэтому задача может быть повторена.

Вложения заявки загружаются вместе с заявкой и пересылаются фактическому получателю после выхода из очереди. Поддерживаются изображения, голосовые и аудиосообщения, видео и файлы. Сообщения клиента по уже назначенной заявке, полученные вне доступного режима, сохраняются и доставляются сотруднику при следующей обработке очереди.

## Продление при обращении в техподдержку

Если подписка активна, пользователь продолжает обычный сценарий техподдержки.

Если подписка отсутствует или истекла, бот предлагает продление. После подтверждения сохраняется предусмотренная бизнес-требованием пара:

- `RENEWAL` для менеджера клиента;
- `TECHNICAL_SUPPORT` для специалиста техподдержки.

Активными для защиты от дублей считаются статусы `NEW`, `IN_PROGRESS` и `WAITING_CLIENT`.

## Статусы и закрытие

Основные статусы: `NEW`, `IN_PROGRESS`, `WAITING_CLIENT`, `CLOSED`, `CANCELLED`.

Закрытие идемпотентно: перед изменением строка заявки блокируется в БД, а повторная попытка для `CLOSED` или `CANCELLED` завершается без повторного уведомления, NPS, записи закрытия и вызова i-TAT.

После первого успешного закрытия клиент получает одно итоговое сообщение с номером заявки и комментарием сотрудника. NPS не создаётся для административных конфликтов ключей.

## Эскалация

Эскалация запускается только после фактической отправки заявки сотруднику. Для заявки из очереди отсчёт начинается после выхода в подходящий режим, а не в момент создания.

Общий порядок: назначенный сотрудник → резерв 1 → резерв 2 → администраторы. Интервалы и каналы задаются настройками системы. Терминальные заявки и повторно доставленные Celery-задачи пропускаются.

## Конфликт ключа

Конфликт ключа является административной операцией, а не обычной пользовательской заявкой:

- ключ получает `GS_Key.conflict_status=PENDING_REVIEW`;
- факт фиксируется в `Action_Log`;
- все активные администраторы уведомляются сразу, независимо от рабочего режима;
- конфликтующий ключ отмечается `⚠️`, блокируется для выбора и получает пояснение;
- операция не участвует в очереди заявок, round-robin, дежурствах, NPS и стандартной эскалации.

Проверка выполняется через i-TAT API. При ошибке или некорректном ответе используется локальная проверка уникальности. После передачи или отклонения обновляются `GS_Key` и `Action_Log`; старые legacy-заявки `KEY_CONFLICT` закрываются.
