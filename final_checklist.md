1. РЕГИСТРАЦИЯ ПОЛЬЗОВАТЕЛЯ
════════════════════════════════════════════════════════════

── 1.1 Новый пользователь ──────────────────────────────────
-  /start → показывает приветствие и кнопку «Поделиться номером»
-  Нажать «Поделиться номером» → бот получает контакт (VCF парсинг)
-  Ввести ФИО (минимум 2 слова) → принято, запрос email
-  Пропустить email → переход к вводу ИНН
-  Ввести email → валидация, переход к ИНН
-  Ввести ИНН (10 или 12 цифр) → проверка через i-TAT API
-  Ввести ключ ГС (формат 00001_00011) → проверка конфликта
-  Регистрация отправлена → статус PENDING, сообщение «Ожидайте»
-  Уведомление администраторам о новой регистрации отправлено

── 1.2 Конфликт ключа при регистрации ─────────────────────
-  Ввести ключ, уже занятый другим пользователем → показывает конфликт
-  Кнопка «Попробовать другой ключ» → возврат к вводу ключа
-  Кнопка «Продолжить с конфликтом» → ключ добавлен со статусом PENDING_REVIEW
-  Уведомление администраторам о конфликте отправлено

── 1.3 Отмена регистрации ──────────────────────────────────
-  Кнопка «Отмена» на любом шаге → FSM очищен, частичная запись удалена
-  Повторный /start → регистрация начинается заново

── 1.4 Уже зарегистрированный пользователь ────────────────
-  /start при статусе ACTIVE → главное меню с inline-клавиатурой
-  /start при статусе PENDING → сообщение «Ожидайте одобрения»

── 1.5 Вебхук одобрения регистрации ───────────────────────
🚩  [i-TAT] POST /registration_status с status=approved → пользователь активирован
-  Менеджер назначен, статус подписки установлен
-  Уведомление пользователю отправлено
🚩  [i-TAT] POST /registration_status с status=rejected → пользователь уведомлён
-  Запрос без API-ключа → 401 Unauthorized
-  Несуществующий пользователь → 404 Not Found

2. ПОЛУЧИТЬ СЧЁТ (Invoice)
════════════════════════════════════════════════════════════

── 2.1 Запуск потока ───────────────────────────────────────
-  Кнопка «💰 Получить счёт» в главном меню → список организаций
-  /invoice команда → то же самое

── 2.2 Выбор организации ───────────────────────────────────
-  Список организаций с пагинацией (7 на страницу)
-  Выбрать существующую организацию → переход к выбору ключей
-  Кнопка «Добавить новый ИНН» → запрос ввода ИНН
-  Ввести новый ИНН → проверка i-TAT API, добавление в профиль
-  Кнопка «Пропустить» → переход к выбору ключей без организации
-  Кнопка «Отмена» → главное меню

── 2.3 Выбор ключей ────────────────────────────────────────
-  Список ключей с чекбоксами (мультивыбор)
-  Ключ со статусом PENDING_REVIEW — нельзя выбрать (предупреждение)
-  Пагинация ключей работает
-  Кнопка «Добавить новый ключ» → ввод ключа ГС
-  Новый ключ с конфликтом → уведомление, ключ добавлен как PENDING_REVIEW
-  Кнопка «Готово» → переход к описанию
-  Кнопка «Пропустить» → переход к описанию без ключей
-  Кнопка «Назад» → возврат к выбору организации

── 2.4 Описание и вложения ─────────────────────────────────
-  Ввести текст описания (до 1000 символов) → принято
-  Текст > 1000 символов → ошибка валидации
-  Отправить фото → добавлено как вложение
-  Отправить голосовое → добавлено как вложение
-  Отправить документ → добавлено как вложение
-  Кнопка «Пропустить описание» → переход к доставке

── 2.5 Способ доставки ─────────────────────────────────────
-  Кнопка «💬 В чат» → переход к подтверждению
-  Кнопка «📧 На Email» → если email есть в профиле, предложить использовать
-  Подтвердить email из профиля → переход к подтверждению
-  Ввести новый email → валидация, переход к подтверждению
-  Кнопка «Назад» → возврат к описанию

── 2.6 Подтверждение и создание заявки ─────────────────────
-  Экран подтверждения показывает: организацию, ключи, описание, способ доставки
-  Кнопка «Подтвердить» → заявка создана с типом INVOICE
-  Кнопка «Заполнить заново» → возврат к выбору организации
-  Кнопка «Отмена» → главное меню
-  Уведомление менеджеру отправлено (в рабочее время)
-  В нерабочее время → заявка в очереди, уведомление утром
-  Вложения переданы менеджеру
-  Главное меню показано после создания заявки

3. ТЕХНИЧЕСКАЯ ПОДДЕРЖКА (Support)
════════════════════════════════════════════════════════════

── 3.1 Запуск потока ───────────────────────────────────────
-  Кнопка «🆘 Техподдержка» → проверка статуса подписки
-  Подписка ACTIVE → запрос описания проблемы
-  Подписка EXPIRED → предложение продлить
-  Подписка NONE → предложение связаться с менеджером

── 3.2 Описание проблемы ───────────────────────────────────
-  Ввести текст (до 4000 символов) → принято
-  Текст > 4000 символов → ошибка валидации
-  Отправить фото → добавлено как вложение
-  Отправить голосовое → добавлено как вложение
-  Отправить документ → добавлено как вложение
-  Кнопка «Пропустить» → переход к выбору ключей без описания

── 3.3 Контекст ключей ─────────────────────────────────────
-  Список ключей с мультивыбором
-  Ключ PENDING_REVIEW — нельзя выбрать
-  Кнопка «Добавить новый ключ» → ввод ключа ГС
-  Кнопка «Готово» → создание заявки
-  Кнопка «Пропустить» → создание заявки без ключей
-  Кнопка «Назад» → возврат к описанию

── 3.4 Создание заявки ─────────────────────────────────────
-  Заявка создана с типом TECHNICAL_SUPPORT
-  В рабочее время → уведомление всем сотрудникам ТП
-  В продлённое время → уведомление дежурному инженеру
-  В нерабочее время → заявка в очереди
-  Нет сотрудников ТП → уведомление администраторам
-  Вложения переданы сотрудникам ТП
-  Эскалация запланирована (Celery задача)
-  Главное меню показано после создания

── 3.5 Отмена ──────────────────────────────────────────────
-  Кнопка «Отмена» на любом шаге → FSM очищен, главное меню

4. КОНСУЛЬТАЦИЯ (Consultation)
════════════════════════════════════════════════════════════

── 4.1 Запуск потока ───────────────────────────────────────
-  Кнопка «💬 Консультация» → список организаций
Проверка подписки: Выполняется сразу Если подписка НЕ ACTIVE: 
✅️/❌/⚠️ || ☑️/✖️ Консультация блокируется Автоматически создаётся заявка RENEWAL
✅️/❌/⚠️ || ☑️/✖️ Заявка отправляется закреплённому менеджеру пользователя
✅️/❌/⚠️ || ☑️/✖️ Показывается сообщение пользователю (разное для EXPIRED и NONE)
✅️/❌/⚠️ || ☑️/✖️ Показывается главное меню
Если подписка ACTIVE:
✅️/❌/⚠️ || ☑️/✖️ Консультация разрешена
✅️/❌/⚠️ || ☑️/✖️ Переход к выбору организации
✅️/❌/⚠️ || ☑️/✖️ Предотвращение дублик

── 4.2 Выбор организации и ключей ──────────────────────────
-  Аналогично Invoice: выбор организации, добавление нового ИНН, пропуск
-  Аналогично Invoice: выбор ключей, добавление нового, пропуск

── 4.3 Описание и создание ─────────────────────────────────
-  Ввести описание (до 4000 символов)
-  Отправить вложения (фото, голосовое, документ)
-  Кнопка «Пропустить описание» → создание без описания
-  Заявка создана с типом CONSULTATION
-  Уведомление сметным специалистам (is_estimate_tech_specialist=True)
-  Нет специалистов → уведомление администраторам с пояснением
-  В нерабочее время → заявка в очереди
-  Вложения переданы специалистам
-  Эскалация запланирована

5. ПРОДЛЕНИЕ ПОДПИСКИ (Renewal)
════════════════════════════════════════════════════════════

── 5.1 Просмотр статуса ────────────────────────────────────
-  Кнопка «🔄 Продление» → показывает статус подписки
-  Статус ACTIVE → дата окончания, количество дней, кнопка «Продлить»
-  Статус EXPIRED → дата истечения, дней прошло, кнопка «Продлить»
-  Статус NONE → кнопка «Связаться с менеджером»
-  Кнопка «В меню» → главное меню

── 5.2 Создание заявки на продление ────────────────────────
-  Кнопка «Продлить» → проверка дублирующей заявки
-  Активная заявка уже есть → сообщение «Уже есть заявка #N», уведомление менеджеру
-  Нет активной заявки → создание заявки RENEWAL
-  Одновременно создаётся заявка TECHNICAL_SUPPORT (для специалиста)
-  Менеджер уведомлён (в рабочее время)
-  В нерабочее время → заявки в очереди
-  Главное меню показано после создания

── 5.3 Вебхук изменения подписки ───────────────────────────
❗  [i-TAT] POST /subscription_status_change с status=active → подписка активирована
-  Дата окончания обновлена
-  Уведомление пользователю отправлено
❗  [i-TAT] POST /subscription_status_change с status=expired → подписка истекла
-  Запрос без API-ключа → 401
-  Несуществующий пользователь → 404

6. ПРОФИЛЬ ПОЛЬЗОВАТЕЛЯ
════════════════════════════════════════════════════════════

── 6.1 Просмотр профиля ────────────────────────────────────
-  /profile → показывает ФИО, телефон, email, организации, ключи, подписку, уведомления
-  Организаций > 10 → показывает первые 10 + «и ещё N»
-  Ключей > 10 → показывает первые 10 + «и ещё N»
-  Ключ PENDING_REVIEW → отмечен ⚠️

── 6.2 Управление организациями ────────────────────────────
-  Кнопка «Мои организации» → список с пагинацией (7 на страницу)
-  Кнопка «Добавить ИНН» → ввод ИНН, проверка i-TAT, добавление
-  Дублирующий ИНН → сообщение «Уже добавлен»
-  Кнопка удаления организации → подтверждение → удаление из БД и i-TAT API

── 6.3 Управление ключами ──────────────────────────────────
-  Кнопка «Мои ключи» → список с пагинацией
-  Кнопка «Добавить ключ» → ввод, проверка конфликта, добавление
-  Конфликт ключа → статус PENDING_REVIEW, уведомление администраторам
-  Кнопка удаления ключа → подтверждение → удаление из БД и i-TAT API

── 6.4 Изменение email ─────────────────────────────────────
-  Кнопка «Изменить email» → ввод нового email
-  Ввести «удалить» → email удалён из профиля
-  Невалидный email → ошибка валидации

── 6.5 Смена номера телефона ───────────────────────────────
Подготовка: два зарегистрированных аккаунта — Пользователь А (старый номер)
            и Пользователь Б (новый номер, уже в системе).

  Запуск и ввод номера
  -  Кнопка «📱 Изменить телефон» в профиле → показывается инструкция
  -  FSM состояние ProfileStates.changing_phone установлено
  -  Показана кнопка «❌ Отмена»

  Валидация номера
  -  Ввести невалидный номер (буквы, короткий) → ошибка валидации, кнопка «Отмена» остаётся
  -  Ввести текущий номер пользователя → сообщение «Смена не требуется», FSM очищен
  -  Ввести номер, не зарегистрированный в боте → сообщение «Номер не найден в системе»
  -  Ввести номер пользователя без max_user_id/max_chat_id → «Аккаунт не привязан к MAX»

  Экран подтверждения
  -  Ввести корректный номер → показывается карточка подтверждения
  -  Карточка содержит: старый номер, новый номер, ФИО владельца нового номера
  -  Карточка содержит описание последствий (перенос данных, удаление старого аккаунта)
  -  Кнопки «✅ Подтвердить» и «❌ Отмена» присутствуют
  -  FSM состояние сохранено (ожидает callback)

  Отмена
  -  Нажать «❌ Отмена» → сообщение «Смена номера отменена», FSM очищен, показан профиль
  -  Reply-кнопка «❌ Отмена» в состоянии changing_phone → аналогично

  Подтверждение и создание заявки
  -  Нажать «✅ Подтвердить» → карточка удалена (replace-message), FSM очищен
  -  Создана заявка типа PHONE_CHANGE со статусом NEW
  -  Заявка содержит old_phone и new_phone
  -  Описание заявки содержит user_id и max_user_id целевого аккаунта
  -  Событие записано в Action_Log (phone_change_requested)
  -  Логирование в i-TAT API выполнено (или поставлено в очередь)
  -  Пользователю показано подтверждение с номером заявки
  -  После подтверждения показан профиль

  Уведомление администраторам
  -  Все активные администраторы с max_chat_id получили уведомление
  -  Уведомление содержит: данные заявителя, данные целевого аккаунта, номер заявки, дату
  -  Уведомление содержит предупреждение о последствиях операции
  -  Кнопка «🔍 Детали операции» присутствует в уведомлении
  -  Нажать «🔍 Детали операции» → карточка с кнопками «✅ Одобрить» и «❌ Отклонить»

  Одобрение администратором
  -  Нажать «✅ Одобрить» → вызов i-TAT API change_phone с user_id целевого аккаунта
  -  i-TAT API недоступен → операция поставлена в очередь повторов, одобрение продолжается
  -  Заявка закрыта (status=CLOSED, closed_at установлен, resolution_comment заполнен)
  -  Перенос данных (проверить в БД):
      -  Все тикеты Пользователя А → переназначены на Пользователя Б
      -  Все ключи ГС Пользователя А → переназначены на Пользователя Б
      -  Организации Пользователя А → добавлены к Пользователю Б (дубли пропущены)
      -  Назначения менеджеров Пользователя А → перенесены (дубли пропущены)
      -  notification_events → перенесены
      -  broadcast_deliveries → перенесены (дубли пропущены)
      -  action_logs → перенесены
      -  api_retry_queue → перенесены
      -  nps_responses → перенесены
      -  max_messenger_data Пользователя А → удалена (Пользователь Б сохраняет свою)
      -  default_manager_id — если у Пользователя Б не было, унаследован от А
  -  Аккаунт Пользователя А удалён из таблицы users
  -  Уведомление Пользователю Б: номер изменён, данные перенесены, заявка закрыта
  -  Администратор видит сообщение «✅ Запрос одобрен»
  -  Кнопка «◀️ К списку запросов» работает

  Отклонение администратором
  -  Нажать «❌ Отклонить» → заявка закрыта со статусом CLOSED
  -  resolution_comment содержит причину отклонения
  -  Аккаунт Пользователя А не удалён, данные не перенесены
  -  Уведомление Пользователю А: запрос отклонён, причина, номер заявки
  -  Администратор видит сообщение «❌ Запрос отклонён»

  Граничные случаи
  -  Целевой аккаунт удалён между подтверждением и одобрением → администратор видит ошибку
  -  Повторное нажатие «Одобрить» на уже закрытой заявке → корректная обработка
  -  Пользователь А нажимает «Отмена» после карточки подтверждения → FSM очищен, заявка не создана

-  Невалидные данные → 400 Bad Request

── 11.2 Статус заявки (POST /ticket_status_update) ─────────
❗  [i-TAT] Отправить status=in_progress → заявка обновлена, уведомление пользователю
❗  [i-TAT] Отправить status=waiting_client → заявка обновлена, уведомление пользователю

❗  [i-TAT] Отправить status=cancelled → заявка отменена, уведомление

❗  [i-TAT] subscription_status=none → подписка удалена
-  Уведомление пользователю отправлено

-  Поддержка messenger=max и messenger=telegram

════════════════════════════════════════════════════════════
12. ФОНОВЫЕ ЗАДАЧИ (Celery)
════════════════════════════════════════════════════════════

── 12.1 Обработка заявок из очереди ────────────────────────
-  Задача запускается в начале рабочего времени (8:00 МСК)
-  Находит заявки NEW за последние 72 часа без queue_notification_sent_at
-  Invoice заявки → уведомление менеджеру + вложения
-  Renewal заявки → уведомление менеджеру
-  Support заявки → уведомление всем администраторам + дежурный канал
-  Consultation заявки → уведомление сметным специалистам
-  После отправки → queue_notification_sent_at установлен (нет дублей)
-  В нерабочее время → задача пропускается

── 12.2 Эскалация техподдержки ─────────────────────────────
-  Задача запускается через N минут после создания заявки ТП
-  Заявка не взята в работу → эскалация создана
-  Уведомление администраторам и дежурному каналу
-  Заявка взята в работу → эскалация не создаётся

── 12.3 Очередь повторных запросов к i-TAT API ─────────────
-  Неудачный запрос → запись в API_Retry_Queue
-  Повторные попытки с экспоненциальной задержкой (5м → 15м → 30м → 1ч → 2ч)
-  Успешный повтор → статус SUCCESS
-  После 5 попыток → статус FAILED, уведомление администраторам
-  Ошибки 4xx → не повторяются (NonRetryableAPIError)
-  Очистка старых записей (> 30 дней)

14. ГРАНИЧНЫЕ СЛУЧАИ И БЕЗОПАСНОСТЬ
════════════════════════════════════════════════════════════

── 14.1 Валидация данных ───────────────────────────────────
-  Телефон: только российский формат +7XXXXXXXXXX
-  Email: стандартный формат RFC
-  ИНН: 10 или 12 цифр
-  Ключ ГС: формат XXXXX_XXXXX
-  Текст > лимита → ошибка с указанием лимита

── 14.2 Контроль доступа ───────────────────────────────────
-  Пользователь видит только свои заявки
-  Менеджер видит только назначенные заявки
-  Команды /manager и /admin — только для сотрудников
-  Админ-панель — только для администраторов
-  Вебхуки — только с валидным API-ключом

── 14.3 Устойчивость ───────────────────────────────────────
-  Удалённое сообщение → бот не падает (обрабатывает исключение)
-  Недоступный i-TAT API → операция ставится в очередь повторов
-  Ошибка БД → пользователь получает ERROR_GENERAL, ошибка залогирована
-  Повторное нажатие кнопки → идемпотентность (нет дублей заявок)
-  FSM состояние потеряно → fallback через БД по max_user_id

── 14.4 Replace-message паттерн ────────────────────────────
-  Все callback-обработчики удаляют старое сообщение перед отправкой нового
-  Ошибка удаления → залогирована как warning, поток продолжается
-  Отмена потока → старое сообщение удалено, показано главное меню
