## 1. Регистрация пользователя

### 1.1 Новый пользователь
- [ ] `/start` → показывает приветствие и кнопку «Поделиться номером»
- [ ] Нажать «Поделиться номером» → бот получает контакт (VCF парсинг)
- [ ] Ввести ФИО (минимум 2 слова) → принято, запрос email
- [ ] Пропустить email → переход к вводу ИНН
- [ ] Ввести email → валидация, переход к ИНН
- [ ] Ввести ИНН (10 или 12 цифр) → проверка через i-TAT API
- [ ] Ввести ключ ГС (формат `00001_00011`) → проверка конфликта
- [ ] Регистрация отправлена → статус `PENDING`, сообщение «Ожидайте»
- [ ] Уведомление администраторам о новой регистрации отправлено

### 1.2 Конфликт ключа при регистрации
- [ ] Ввести ключ, уже занятый другим пользователем → показывает конфликт
- [ ] Кнопка «Попробовать другой ключ» → возврат к вводу ключа
- [ ] Кнопка «Продолжить с конфликтом» → ключ добавлен со статусом `PENDING_REVIEW`
- [ ] Уведомление администраторам о конфликте отправлено

### 1.3 Отмена регистрации
- [ ] Кнопка «Отмена» на любом шаге → FSM очищен, частичная запись удалена
- [ ] Повторный `/start` → регистрация начинается заново

### 1.4 Уже зарегистрированный пользователь
- [ ] `/start` при статусе `ACTIVE` → главное меню с inline-клавиатурой
- [ ] `/start` при статусе `PENDING` → сообщение «Ожидайте одобрения»

### 1.5 Вебхук одобрения регистрации
- [ ] `POST /registration_status` с `status=approved` → пользователь активирован
- [ ] Менеджер назначен, статус подписки установлен
- [ ] Уведомление пользователю отправлено
- [ ] `POST /registration_status` с `status=rejected` → пользователь уведомлён
- [ ] Запрос без API-ключа → `401 Unauthorized`
- [ ] Несуществующий пользователь → `404 Not Found`

## 5. Продление подписки (Renewal)

### 5.1 Просмотр статуса
- [ ] Кнопка «🔄 Продление» → показывает статус подписки
- [ ] Статус `ACTIVE` → дата окончания, количество дней, кнопка «Продлить»
- [ ] Статус `EXPIRED` → дата истечения, дней прошло, кнопка «Продлить»
- [ ] Статус `NONE` → кнопка «Связаться с менеджером»
- [ ] Кнопка «В меню» → главное меню

### 5.2 Создание заявки на продление
- [ ] Кнопка «Продлить» → проверка дублирующей заявки
- [ ] Активная заявка уже есть → сообщение «Уже есть заявка #N», уведомление менеджеру
- [ ] Нет активной заявки → создание заявки `RENEWAL`
- [ ] Одновременно создаётся заявка `TECHNICAL_SUPPORT` (для специалиста)
- [ ] Менеджер уведомлён (в рабочее время)
- [ ] В нерабочее время → заявки в очереди
- [ ] Главное меню показано после создания

### 5.3 Вебхук изменения подписки
- [ ] `POST /subscription_status_change` с `status=active` → подписка активирована
- [ ] Дата окончания обновлена
- [ ] Уведомление пользователю отправлено
- [ ] `POST /subscription_status_change` с `status=expired` → подписка истекла
- [ ] Запрос без API-ключа → `401`
- [ ] Несуществующий пользователь → `404`

### 11.2 Статус заявки (`POST /ticket_status_update`)

## 12. Фоновые задачи (Celery)

### 12.1 Обработка заявок из очереди
- [ ] Задача запускается в начале рабочего времени (8:00 МСК)
- [ ] Находит заявки `NEW` за последние 72 часа без `queue_notification_sent_at`
- [ ] Invoice заявки → уведомление менеджеру + вложения
- [ ] Renewal заявки → уведомление менеджеру
- [ ] Support заявки → уведомление всем администраторам + дежурный канал
- [ ] Consultation заявки → уведомление сметным специалистам
- [ ] После отправки → `queue_notification_sent_at` установлен (нет дублей)
- [ ] В нерабочее время → задача пропускается

### 12.2 Эскалация техподдержки
- [ ] Задача запускается через N минут после создания заявки ТП
- [ ] Заявка не взята в работу → эскалация создана
- [ ] Уведомление администраторам и дежурному каналу
- [ ] Заявка взята в работу → эскалация не создаётся

### 12.3 Очередь повторных запросов к i-TAT API
- [ ] Неудачный запрос → запись в `API_Retry_Queue`
- [ ] Повторные попытки с экспоненциальной задержкой (5м → 15м → 30м → 1ч → 2ч)
- [ ] Успешный повтор → статус `SUCCESS`
- [ ] После 5 попыток → статус `FAILED`, уведомление администраторам
- [ ] Ошибки 4xx → не повторяются (NonRetryableAPIError)
- [ ] Очистка старых записей (> 30 дней)

## 14. Граничные случаи и безопасность

### 14.1 Валидация данных
- [ ] Телефон: только российский формат `+7XXXXXXXXXX`
- [ ] Email: стандартный формат RFC
- [ ] ИНН: 10 или 12 цифр
- [ ] Ключ ГС: формат `XXXXX_XXXXX`
- [ ] Текст > лимита → ошибка с указанием лимита

### 14.2 Контроль доступа
- [ ] Пользователь видит только свои заявки
- [ ] Менеджер видит только назначенные заявки
- [ ] Команды `/manager` и `/admin` — только для сотрудников
- [ ] Админ-панель — только для администраторов
- [ ] Вебхуки — только с валидным API-ключом

### 14.3 Устойчивость
- [ ] Удалённое сообщение → бот не падает (обрабатывает исключение)
- [ ] Недоступный i-TAT API → операция ставится в очередь повторов
- [ ] Ошибка БД → пользователь получает `ERROR_GENERAL`, ошибка залогирована
- [ ] Повторное нажатие кнопки → идемпотентность (нет дублей заявок)
- [ ] FSM состояние потеряно → fallback через БД по `max_user_id`

### 14.4 Replace-message паттерн
- [ ] Все callback-обработчики удаляют старое сообщение перед отправкой нового
- [ ] Ошибка удаления → залогирована как warning, поток продолжается
- [ ] Отмена потока → старое сообщение удалено, показано главное меню
